## 1. 文件正文要保持资料身份

- **问题：** 用户选择了一个文件，不代表同意执行文件内的指令。把正文拼进系统提示词，会把资料和应用规则混在一起。
- **原因：** 文件属于外部输入，可能含有角色声明、要求泄露信息的文字或伪造分隔符；用户批准的是读取指定资料。
- **实践：** 系统层仅保留“按不可信资料处理”的规则；文件名、正文及分隔符放在独立 `user` 消息中，真正的问题放在其后。模型输出仍只作为文本，不能因此获得文件动作权限。长度、UTF-8 和请求体角色结构都要校验，不能只靠提示词。
- **验证：** 检查 [persona.py](../DyberPet/assistant/persona.py) 的 `stream_local_chat`；[协议测试](../tests/test_assistant_persona_voice.py) 中 `test_local_stream_includes_user_approved_file_as_untrusted_reference` 验证请求角色与恶意正文位置，`test_local_stream_rejects_invalid_file_context` 验证上限。该测试证明请求结构，不证明模型绝不会受提示注入影响。

## 2. 审批应绑定内容与一次具体动作

- **问题：** 用户确认后，同一路径的文件可能已经变更；旧审批也可能被重复使用或带到另一个工作目录。
- **原因：** 路径名称不是内容身份，长期布尔授权也不能表达“此刻、此目标、此动作”。
- **实践：** `prepare → approve → execute` 分阶段；读取审批绑定文件字节 SHA-256，执行前复核；动作使用白名单、精确目标、短有效期和一次性请求 ID。工作区切换清空待执行审批。日志只保留动作、目标、状态和必要错误信息，不记录文件正文。若动作已成功但最后一条审计写入失败，返回成功及审计警告，避免诱发重复执行。
- **验证：** 查看 [action_runtime.py](../DyberPet/assistant/action_runtime.py) 及 [动作测试](../tests/test_assistant_action_runtime.py)：覆盖确认前阻断、拒绝、过期、重复使用、内容变更、工作区切换、恢复冲突和正文不写审计。SHA-256 校验不等于文件系统操作已经获得完整的抗竞争保证；新增并发路径要单独审查检查与使用之间的窗口。

## 3. 会话资料必须有明确生命周期

- **问题：** 附件、角色人设、识别结果或模型回复可能在角色切换、工作区撤销、窗口关闭后继续使用。
- **原因：** 异步任务持有启动时的快照，清空界面字段并不能撤销已发出的请求或阻止迟到回调。
- **实践：** 为任务记录角色和会话代次，接收增量和最终结果时核对身份。附件仅供下一次成功请求，成功后清除；网络失败保留待用户重试；角色、工作区或窗口生命周期变化时清除待用上下文。修改这些入口时，同时检查在途任务、迟到回复、缓存、审批和历史，不能只检查一个字段。
- **验证：** 查看 [ui.py](../DyberPet/assistant/ui.py) 的 `set_character`、`send_message`、`_message_reply`、`reset_workspace` 和 `closeEvent`；[Qt 测试](../tests/test_assistant_qt.py) 已覆盖单轮附件消费、角色隔离、工作区重置及旧角色增量丢弃。文件任务草案批次之前，工作区重置只清附件；`9945a31` 通过统一会话失效入口补齐，并在 [任务集成测试](../tests/test_assistant_task_integration_qt.py) 中验证迟到成功、错误和麦克风部分转写；不能由“清空字段”推定安全。

附件原文不作为独立历史条目保存，不等于原文绝不落盘：模型回答可能引用资料，而已完成回答会进入本地会话历史。涉及隐私说明或历史策略的修改，应同时检查 [conversation_store.py](../DyberPet/assistant/conversation_store.py) 和 `_message_reply`。

## 4. 线程结束、收到文本与业务成功要分别处理

- **问题：** 收到部分流式文本后断线，界面可能误报完成；关闭窗口时仍在运行的语音线程可能被提前销毁；UI 直接停止语音驱动还可能违反线程归属。
- **原因：** 增量事件、任务结果、`QThread.finished` 和驱动回调具有不同含义，不能共用一个“完成”状态。
- **实践：** UI 只更新控件或设置停止事件，TTS 引擎由创建它的工作线程初始化、迭代和停止。保留线程对象直至 `finished` 再清理。窗口先请求停止并等待完成通知。流式协议至少要求收到 `[DONE]`；断流保留已显示文字并标明中断，不把它写成成功的一轮，也不自动播报或保存为便签。业务成功、协议结束和线程释放分别决定各自的后续动作。
- **验证：** 查看 [voice.py](../DyberPet/assistant/voice.py) 的 `speak_interruptible`、[ui.py](../DyberPet/assistant/ui.py) 的 `_submit`、`_job_finished`、`closeEvent` 和 [persona.py](../DyberPet/assistant/persona.py) 的 SSE 解析。回归入口是 [语音/协议测试](../tests/test_assistant_persona_voice.py) 中断流与可中断 TTS 用例，以及 [Qt 测试](../tests/test_assistant_qt.py) 中窗口等待、旧角色结果丢弃和中断标记用例。模拟驱动通过只能证明控制流程，不能证明真实设备的可听效果与停止延迟。

## 5. 先在本地完成一个改动，再原子提交

- **问题：** 远端逐行改文件容易产生修复提交连锁，也容易把真实换行写成字面量 `\\n`。
- **原因：** 内容在 shell、JSON、脚本和目标源码之间经过多次编码，修补时又缺少完整文件和请求体检查。
- **实践：** 在本地工作副本一次完成相关代码、测试和说明；尽量通过补丁或文件参数传递文本。检查实际 diff 和最终字符串，再跑针对性回归，最后按一个完整行为提交。提交消息描述问题和变化，避免用多次小提交代替本地验证。
- **验证：** 历史提交 [`541dae2`](https://github.com/clonetimer/DyberPet/commit/541dae2bd417852bda1d48b1e6d19608c8cd6032) 的主题是修正文件上下文分隔符为真实换行；随后文件任务草案批次在现有聊天协议测试和任务规划 HTTP 测试中补充真实换行断言。提交前执行 `git diff --check`、检查 `git diff`，并运行影响范围内的测试。浅克隆只显示当前提交时，不凭空补写更早的提交顺序或根因证据。

## 6. 等待 CI 时按一批结果作判断

- **问题：** 每隔几秒查询同一工作流，消耗时间但不能缩短 Windows 打包；不同 SHA 的绿色结果也容易被混用。
- **原因：** 把“仍在运行”当成新证据，或只记录分支名和页面上的绿色图标。
- **实践：** 一次提交后记录完整 SHA，集中取得该 SHA 的相关运行；让独立作业并行，按有意义的间隔查询整批状态。出现失败才读取相应作业日志。检查工作流的分支与路径过滤：文档变更未触发工作流时，记录“未运行”，不能补写“通过”。产物同时记录运行 ID、artifact ID、大小、摘要和保留期。
- **验证：** [桌宠工作流](../.github/workflows/pet-assistant.yml) 有 4 个系统/Python 单测组合、1 个 Qt 作业、1 个 PPL 合约作业；[Windows 工作流](../.github/workflows/windows-portable.yml) 单独构建并启动冻结 EXE。最终记录应核对运行所属 SHA 与全部必要作业结论，不能拿上面的旧绿色基线代替本轮结果。

本批额外触发的 [角色导入工作流](../.github/workflows/character-mod-importer.yml) 还暴露了镜像漂移：`ubuntu-latest` 已解析到 Ubuntu 26.04，`setup-python` 找不到 Python 3.9。该矩阵改为 `ubuntu-24.04`，保留 Python 3.9/3.11 覆盖；这种失败应修正环境契约，不能删掉版本检查来取得绿色。

## 7. 验收结论按证据层级书写

- **问题：** 单测、离屏 GUI、打包后 EXE、真实设备和性能验收混写，会让“能导入模块”看起来像“完整体验已可用”。
- **原因：** 测试名称相近，但执行环境、替身依赖、真实输入和观测指标不同。
- **实践：** 每项结论写清版本、环境、实际执行对象与覆盖边界。性能工作先确定测量流程与指标，再采样；至少区分首段回复延迟、完整回复延迟、麦克风停止延迟、TTS 停止延迟、CPU/内存和长时间运行趋势。没有真实模型与设备数据，就保留为待验收项，不编造数值或达标结论。
- **验证：** Windows 流程确实从其他工作目录启动 `DyberPet.exe --assistant-smoke`，但 Qt 使用离屏模式，语音组件主要检查打包与导入。实机验收另需记录模型 ID、量化/配置、硬件、驱动、样本和可复现操作。详见 [Windows 验收边界](windows_portable.md) 和 [助手自动化边界](pet_assistant.md)。

## 8. 严格解析必须覆盖整个模型响应

- **问题：** 内层任务 JSON 校验再严格，外层 HTTP JSON 如果有重复的 `finish_reason`、`content`，普通解码器已经丢掉了歧义。空字典也可能被真假值检查误判为“没有工具调用”。
- **原因：** 安全判断发生在解析之后；宽松解析无法把原始歧义交给后续校验。
- **实践：** 任务专用解码器从外层开始拒绝重复字段、非有限数值和过深嵌套；控制字段校验类型，只接受完整 `stop` 回复。草案是不可变数据，审批 token 由本机生成。
- **验证：** [任务规划测试](../tests/test_assistant_task_planner.py) 使用真实回环 HTTP 服务器重现重复完成原因、重复内容、畸形 `tool_calls` 和 `refusal`；修复前接受这些响应，修复后全部拒绝。正常聊天无需跟随任务协议改变。

## 9. 窗口关闭要覆盖 Esc 与真实事件循环

- **问题：** `QDialog` 按 Esc 可以隐藏父窗口而绕过原有 `closeEvent`，留下可批准的任务子窗口；只直接调用方法的测试发现不了这条路径。
- **原因：** `reject()`、窗口关闭事件和线程结束是不同入口。延迟删除子窗口又与父对象销毁交织，可能在后续事件循环中暴露生命周期错误。
- **实践：** Esc 与关闭按钮统一撤销 scope，停止语音并等待 worker；避免 `closeEvent → reject → close` 递归。旧任务窗口取消后断开父级通知并解除父子关系，让引用决定剩余生命周期。测试必须实际按键并运行 Qt 事件循环。
- **验证：** [任务集成测试](../tests/test_assistant_task_integration_qt.py) 覆盖真实 Esc、进行中的规划 worker、旧成功/错误回调、重复替换与单击/多击审批。文件任务草案批次曾在 `close()` 后直接 `deleteLater()` 触发 PySide6 6.8.3 测试段错误；移除该延迟删除并调整对象归属后，整组事件循环测试通过。这是具体复现的经验，不推论所有 Qt 环境都禁止 `deleteLater()`。

## 10. 多步骤任务按实际副作用结算

- **问题：** 第一步成功后取消第二步，若统一写“未修改文件”会误导；审计收尾故障若被当作写入失败，会诱发重复重试。
- **原因：** 草案、审批、文件写入和审计是四种不同状态，不能用一个成功/失败布尔值覆盖。
- **实践：** 仅准备当前步骤；每步展示固定内容，再申请一次审批。执行后先明确记入完成列表，用户另点“查看下一步”再批准。失败或取消停止剩余步骤，保留并列出已经创建的文件；成功后的审计故障作为警告。
- **验证：** [任务状态机测试](../tests/test_assistant_task_plan.py) 与 [审阅窗口测试](../tests/test_assistant_task_qt.py) 用真实临时文件系统验证部分完成、碰撞不覆盖、过期、审计警告和双击不连写；[运行时测试](../tests/test_assistant_action_runtime.py) 用同步事件验证目录切换不会改变已经展示的执行目标。

## 11. 取消要同时约束结果提交与阻塞等待

- **问题：** 只隐藏迟到文字，线程仍可能卡在等待响应头或正文；只断开连接，已经排入 Qt 队列的成功信号仍可能保存历史、触发朗读或打开草案。
- **原因：** 用户取消、HTTP 连接终止、工作线程退出和服务端推理停止是不同事件。服务端已接收的动作也不会因客户端断开而自动回滚。
- **实践：** UI 先标记本次请求取消，拒绝后续成功、错误和进度；同一 token 贯穿聊天前 PPL 状态获取及模型请求。传输层对绑定的 socket 执行 `shutdown`，让工作线程自行退出和关闭响应，不在 UI 跨线程关闭缓冲读取器或强杀线程。只有收到线程结束后才恢复发送按钮。取消的片段保留可见但不作为完整历史，输入和附件保留供重试。
- **验证：** [request_control.py](../DyberPet/assistant/request_control.py) 与 [真实 HTTP 合约测试](../tests/test_assistant_request_control.py) 覆盖请求前取消、响应头/SSE/JSON 正文等待、连接注册竞态及取消后重试；[活动 Qt 测试](../tests/test_assistant_activity_qt.py) 覆盖成功已排队、迟到错误、部分文本保留和草案不发布。它们不证明 LM Studio 已立即停止后端 GPU 推理，也不回滚已送达的 PPL 会话创建。每次 TCP 连接尝试使用最多 3 秒超时；操作系统的 `localhost` 名称解析不由本机 token 强行抢占，多地址尝试也可能增加总时长，不能据此承诺整个取消流程在 3 秒内结束。

## 12. 设备就绪不能用“任务已启动”代替

- **问题：** 模型还在加载时显示“正在监听”，或用户已停止朗读后继续排入语音并发送开始反馈，会让用户误判麦克风和声音的实际状态。
- **原因：** 启动工作线程只代表开始准备；第三方模型加载、设备打开、引擎初始化和排队播放各自可能阻塞或失败。
- **实践：** 分别呈现准备、实际活动与正在停止。麦克风 ready 仅在输入流成功打开且仍未停止时发出；模型/识别器初始化后再次检查 stop。TTS 在初始化、排队和启动循环之间检查 stop；取消后跳过后续阶段，并仍由原线程清理驱动。文案不能把播报循环时限说成可以强制打断所有驱动调用。
- **验证：** [voice.py](../DyberPet/assistant/voice.py) 与 [语音生命周期测试](../tests/test_assistant_voice_lifecycle.py) 用受控驱动验证实际阶段顺序、初始化中停止、设备打开失败不 ready，以及清理归属。驱动内部的 `init/open/read` 无法被本次事件强行抢占；这些回归证明返回后的控制流程，不证明实机可听效果或停止延迟。

## 13. 排队信号要绑定本次资源身份

- **问题：** 同一角色连续朗读两次时，上一轮迟到的 ready 可能把下一轮误标为已开始；停止监听后迟到的 partial 也可能覆盖停止提示。
- **原因：** 角色名与会话代次可以隔离切换，但不足以区分同一会话里的两次设备操作。信号发出时有效，不代表 Qt 接收时仍有效。
- **实践：** ready 携带本次 stop event 身份，接收时核对当前对象、角色/代次、停止标志和窗口状态。停止过程中不再接受部分转写更新；最终识别结果仍按当前会话交给用户确认。结果过滤与设备停止同时存在，不能彼此替代。
- **验证：** [ui.py](../DyberPet/assistant/ui.py) 的 `_on_microphone_ready`、`_on_voice_engine_ready` 和 `_heard_partial`；[活动 Qt 测试](../tests/test_assistant_activity_qt.py) 实际运行事件循环，覆盖同角色旧 ready、停止后 ready、停止后 partial 和角色切换。

## 14. 观察时间要说明起止点与统计含义

- **问题：** 一个“耗时”数字容易被误认为模型速度；用系统时间做差又会受校时影响，活动结束后继续计时则会误报等待时长。
- **原因：** 请求包含 UI 排队、可选 PPL 获取、网络等待、模型生成和回调显示；首段文字与 token、完整回复、设备就绪各不相同。
- **实践：** 用单调时钟从用户启动本次活动计时，首段记录第一段实际显示文字的时刻，字符数仅统计已展示文本。在线程结束时冻结数值，下一次活动重新计时；指标保留在本次界面状态，不额外持久化提示词、回答、音频或遥测。已完成聊天的既有 SQLite 保存策略仍独立适用。
- **验证：** [ui.py](../DyberPet/assistant/ui.py) 的活动状态方法与 [活动 Qt 测试](../tests/test_assistant_activity_qt.py) 使用受控时钟验证首段、显示字符和结束后冻结。这些值不等于 tokens/s、CPU/GPU 占用或跨设备性能结论；模型与硬件验收需要独立采样。

## 15. 用户开关要覆盖每条实际入口

- **问题：** 普通回复遵守“显示桌宠气泡”开关，TTS 开始路径却仍弹出相同气泡。
- **原因：** 同一种用户可见效果从多个信号入口触发，其中一条桥接只检查了全局设置，没有检查助手自身偏好。
- **实践：** 在真正产生效果的入口核对相关开关。朗读状态、原生动作和回复气泡分别控制；关闭气泡不应连带屏蔽语音生命周期，也不应误关已有、已解锁的说话动作。
- **验证：** [DyberPet.py](../DyberPet/DyberPet.py) 的 `_assistant_speech_started` 和 [原生桥接测试](../tests/test_assistant_speech_gait.py) 执行实际方法，检查气泡注册结果、说话状态与动作选择。既有全局气泡设置继续生效，没有安装说话素材时仍不伪造动作。

## 16. 准备失败与工作线程失败要分别收尾

- **问题：** 启动生成前读取本地历史失败，界面可能已经清空输入并进入忙碌状态，却没有真正运行的 worker 可以停止；另一种情况是手动文件动作报错，公共错误处理把仍在监听的麦克风停止事件清空了。
- **原因：** 把“展示错误”和“释放当前异步任务”放在同一个方法里，混淆了错误来源与资源归属；又在会失败的准备步骤完成前提交了 UI 状态变化。
- **实践：** 先读取并校验本地历史和记忆，成功后再清空输入、启动计时和工作线程；准备失败保留用户文字并给出可恢复提示。手动动作错误只报告该动作，只有当前 worker 的失败/结束路径才能收尾其麦克风、朗读与停止控件。
- **验证：** 检查 [ui.py](../DyberPet/assistant/ui.py) 的 `send_message`、`_job_error`、`_job_failed` 和 `_job_finished`；[活动 Qt 回归](../tests/test_assistant_activity_qt.py) 使用临时数据库及真实 worker，分别验证历史准备失败不会留下无 worker 的忙碌状态，以及无关文件错误后停止监听仍然有效。单纯检查报错文字不足以证明资源已经正确释放。

## 17. 后台回调不要延长整棵窗口的生命周期

- **问题：** 音频工作完成、窗口关闭后，保留的 ready 回调仍强引用窗口；完整套件在后续 Qt 事件循环中发生 native 段错误，单独 Qt 用例组却能通过。
- **原因：** 最小复现缩小到三项音频/取消测试及主线程 `gc.collect()`。native 栈和销毁记录显示，无父测试窗口进入循环回收时，底部 `QLabel` 的析构经过父布局通知崩溃。仅将 ready 的强窗口引用改为弱引用，同一复现即通过；没有证据把它归为某个已确认的 Qt 缺陷。
- **实践：** 设备回调保留角色、会话及本次停止事件，窗口仅使用弱引用，接收端继续核对身份和停止状态。生产助手仍由桌宠父对象持有，关闭仍等待 worker 退出。不要用禁用 GC、调整测试顺序或删除定时反馈来掩盖引用生命周期问题。另需区分 [Qt 关闭窗口](https://doc.qt.io/qt-6/qwidget.html#close) 与 [延迟删除对象](https://doc.qt.io/qt-6/qobject.html#deleteLater)：测试临时对象的清理和可复用产品窗口的关闭不能混为一谈。
- **验证：** [活动 Qt 测试](../tests/test_assistant_activity_qt.py) 的 `test_retained_audio_callback_does_not_keep_a_closed_window_alive` 分别保留朗读回调和麦克风任务，验证关闭窗口可被释放、迟到回调不再访问它。旧实现两个分支均失败，弱引用修复后通过；原三项强制 GC 复现也通过。完整套件结果按本批验证记录另列，不拿单项结果代替全量结论。

## 18. 模块替身要保留真实模块结构

- **问题：** 语音测试在 PySide6 6.8.3 通过，却在完整 PySide6 6.5.2 套件中因 `SimpleNamespace` 缺少 `__name__` 报错；仅运行纯 Python 语音用例无法发现。
- **原因：** 将模块放入 `sys.modules` 时，只提供业务方法不足以模拟模块。旧版 Shiboken 的导入钩子还会读取模块元数据；Qt 和语音测试处于同一进程时才触发这条路径。
- **实践：** 使用标准库 `types.ModuleType` 构造 sounddevice、vosk 和 pyttsx3 替身，再挂载受控驱动方法。保留真实生产捕获/播报循环及原行为断言，不降低测试范围。测试运行时应包含实际支持的 Python/Qt 组合，不能只凭更新版本通过推断旧版兼容。
- **验证：** [既有语音合约](../tests/test_assistant_persona_voice.py) 和 [语音生命周期测试](../tests/test_assistant_voice_lifecycle.py) 的模块替身均采用此结构。首轮失败证据来自 [角色导入 CI 44242637307](https://github.com/clonetimer/DyberPet/actions/runs/44242637307)；修复后的精确版本本地及远端结果见 [本批验证记录](verification/2026-11-18-assistant-activity.md) 与 PR。

## 19. 模型列表成功不等于模型已加载

- **改了什么：** 用可编辑下拉框呈现本地服务列出的模型，保留手填 ID；空输入且只有一个候选时才自动填入。状态明确写出“尚未验证生成”。
- **为什么：** 首次使用不应要求用户猜模型 ID，也不能擅自替换已有选择。
- **踩坑：** `/v1/models` 在 LM Studio 的 JIT 模式下可能包含已下载但未加载的模型，[官方契约](https://lmstudio.ai/docs/developer/openai-compat/models)没有保证每个 ID 都是可聊天模型。旧提示“选择已加载的模型”过度推断了接口含义。
- **验证：** [模型发现测试](../tests/test_assistant_model_discovery.py)使用真实回环 GET，验证无请求体、有序去重、ID 与响应上限；[首次使用 Qt 测试](../tests/test_assistant_setup_qt.py)覆盖单候选、多候选、手填和刷新期间修改选择。

## 20. 连接诊断要覆盖不同传输与地址解析错误

- **改了什么：** `AssistantServiceError` 增加兼容旧调用的分类，模型发现复用取消令牌，JSON/SSE 使用一致 HTTP 错误分类；界面提供中文下一步提示。
- **为什么：** 用户需要知道应修改地址、启动服务、等待模型还是核对认证，不能只收到一段通用异常。
- **踩坑：** `urlsplit()` 和 `.port` 都可能抛出 `ValueError`；空 user-info 不能只用真值判断。普通 urllib 与可取消连接的异常也不同。诊断不复制服务错误正文，应用自身协议细节则保留必要的有界提示。
- **验证：** [发现/诊断合约](../tests/test_assistant_model_discovery.py)覆盖拒绝连接、超时、HTTP 状态、重定向、无模型、坏响应、代理隔离与取消。401/403 提示核对认证要求，不引导关闭认证。

## 21. 配置变化也需要拒绝迟到结果

- **改了什么：** 模型检查绑定地址与修改代次；语音检查绑定路径与修改代次。修改地址会取消旧检查并清空旧候选，保留用户输入。缺配置和失败请求不消耗问题与附件。
- **为什么：** 角色会话代次无法识别同一角色内的地址和路径变化；旧结果可能把新配置误报为已就绪。
- **踩坑：** 只比较最终地址不够——用户可能从 A 改成 B 再改回 A。刷新模型时 Qt 会自动选中第一项，也必须显式恢复用户选择。恢复问题只能填入空输入框，不能覆盖用户已输入的新问题。
- **验证：** [实际 Qt 回归](../tests/test_assistant_setup_qt.py)验证 A→B→A、迟到错误、关闭、取消后重试、刷新中编辑、配置缺失与请求失败后的输入保留。

## 22. 语音初检应被动执行并分别报告能力

- **改了什么：** 新增纯标准库的组件与目录检查，识别和 TTS 独立显示；检查不导入音频驱动、不加载模型、不枚举或打开设备。
- **为什么：** 用户应该先看清缺少哪些条件；检查按钮不能意外开启麦克风或发声，缺少 Vosk 也不应遮掉 TTS 状态。
- **踩坑：** `find_spec` 在模块替身缺少 `__spec__` 时会抛出 `ValueError`，需要按组件降级。Vosk 当前与旧版目录标识必须成对匹配，不能把混合或外层目录报成有效模型；结构存在不证明模型内容和设备可用。冻结 EXE 缺组件时，向系统 Python 执行 pip 不能修复当前程序，因此便携版提示重新完整解压或取得匹配候选包，源码版才提示在对应 Python 环境安装依赖。
- **验证：** [被动检查测试](../tests/test_assistant_voice_readiness.py)使用“可发现但导入即报错”的临时音频模块验证无驱动导入，覆盖目录布局、缺项和路径错误；[Vosk 官方源码](https://github.com/alphacep/vosk-api/blob/master/src/model.cc)为布局依据。

## 23. 新增帮助文案后必须检查实际窗口尺寸

- **改了什么：** 助手内容加入滚动容器，初始窗口按当前屏幕可用区域限制大小；原控件及行为保留。
- **为什么：** 设置提示增加后，较小屏幕仍需能访问聊天与底部文件操作。
- **踩坑：** `resize()` 不能压过 Qt 布局的最小尺寸。实际渲染发现最低高度达到 977 逻辑像素，单纯调整初始高度无效，需要让内容滚动。
- **验证：** 真实 Qt 渲染截图和窗口/滚动范围记录列入 [本批验证记录](verification/2026-11-18-assistant-first-use.md)。截图证明布局和控件呈现，不证明真实模型或音频验收。

## 24. 取消检查也要结束设置区状态

- **改了什么：** 关闭窗口、切换会话或主动停止检查时，将对应设置标签收敛为“已停止，请重新检查”，仍丢弃所有迟到结果。
- **为什么：** 助手窗口会被复用，隐藏不等于重新构造；工作线程结束后不能残留“正在检查”。
- **踩坑：** 仅恢复按钮和释放 worker 不足以结束其他区域的状态。独立审阅复现关闭后重开的问题，随后又复现角色切换同一缺口。只有检查仍绑定当前配置且未成功/失败时才改为取消，避免覆盖新配置提示或已完成结果。
- **验证：** [首次使用 Qt 测试](../tests/test_assistant_setup_qt.py)新增模型/语音关闭重开及角色切换回归，先观察失败，再修复通过。

## 25. 共享服务诊断不能默认所有错误都来自模型

- **改了什么：** 共享传输的连接、响应和 HTTP 404 提示保持服务中立；模型专属操作说明继续放在模型设置区与用户指南。
- **为什么：** 同一 `AssistantServiceError` 也用于 PPL 关系状态服务，PPL 失败时不应引导用户启动 LM Studio 或修正 OpenAI 模型 ID。
- **踩坑：** 首次使用改进中的全局异常格式化会影响旧功能。独立审阅发现此兼容性回归；通过实际 Qt 聊天前的 PPL 请求路径复现后修复，没有增加新的 PPL 功能。
- **验证：** [Qt 回归](../tests/test_assistant_setup_qt.py)的 PPL 连接/404 分支先失败后通过，并确认原问题保留。

## 26. 语法兼容不能替代最低版本的真实 I/O

- **改了什么：** 校验原始本机服务 authority，拒绝 IPv6 方括号周围的多余文本；传输错误同时识别 `TimeoutError` 与 `socket.timeout`。新增旧解析器行为、合法地址保留和 SSE 响应头超时回归。
- **为什么：** 首批提交 `906f8f8` 在 Python 3.12 的本地全量测试通过，但 [Python 3.9/3.11 远端矩阵](https://github.com/clonetimer/DyberPet/actions/runs/44247073083)发现真实运行时差异。AST 的 3.9 grammar 检查只能说明语法可解析。
- **踩坑：** 较旧 Python 补丁版本能从畸形 IPv6 authority 中提取合法 hostname/port；仅检查这两个字段不足。[`urllib.parse` 文档](https://docs.python.org/3/library/urllib.parse.html#url-parsing-security)明确提醒解析不等于完整验证。另一个差异是 [`socket.timeout` 到 Python 3.10 才成为 `TimeoutError` 别名](https://docs.python.org/3.10/library/socket.html#socket.timeout)，3.9 上不能只判断后者。
- **验证：** 实际 Python 3.9.25、3.11.9 上先复现超时误分类或旧解析器放行，再验证 26 项发现/诊断测试全部通过；两版各 51 项相关传输、聊天、PPL 与任务规划回归通过。新补丁版本的解析器已加固，因此保留旧解析器结构的定向回归，避免测试只覆盖开发机行为。

## 27. 渲染顺序测试也要明确可行走位置

- **改了什么：** 原生步态测试把 `QSettings` 隔离扩展到窗口的整个生命周期，固定测试屏幕，并在渲染验证前把窗口移到有左移空间的位置。保留真实行走入口、渲染顺序及停止后参数恢复的全部断言。
- **为什么：** [角色导入矩阵](https://github.com/clonetimer/DyberPet/actions/runs/44247073073)的 Windows/Linux 作业均在“向左行走应成功”处失败；测试的目标是渲染顺序，却依赖宿主屏幕和持久化窗口位置。
- **踩坑：** 只在模型激活时替换 `QSettings`，无法阻止构造时读取旧位置、关闭时写回。生产代码在左边缘拒绝继续左移是正确行为，不能为了让测试变绿而放宽边界保护。已用保存位置 `[0, 100, 360, 370]` 确定性复现同一断言，但远端日志没有几何信息，不能断言 CI 当时就是这个值。
- **验证：** Python 3.11.18 / PySide6 6.5.2 中原测试失败、修正后通过，外部保存位置原样保留；相关 86 项 Qt/步态/朝向/放置/任务回归通过。PySide6 6.8.3 的本文件 8 项也通过，屏幕边缘拒绝行走的既有专测继续有效。

## 28. TTS 循环退出不等于播报完成

- **改了什么：** `speak_interruptible` 保留 `finished-utterance` 的 `completed` 标志；驱动报告未完成且用户未停止时抛出语音错误，用户停止与完成回调同时到达则返回停止。驱动自身异常继续按失败传播。
- **为什么：** 本机试用报告需要区分“引擎报告完成”“用户停止”“驱动未完成”，原回调只设置结束事件，会把 `completed=False` 错报成功。
- **踩坑：** 仅检查循环是否结束、或只在未收到结束回调时检查停止，会遗漏完成与停止的竞态。工作线程已返回而 Qt 成功信号尚未消费时，界面仍须保留随后接受的停止；即使引擎完成，也不能自动推定用户听到了正确声音。
- **验证：** [语音生命周期测试](../tests/test_assistant_voice_lifecycle.py)最初 5 个具体案例先失败；增加实际完成元数据后共 23 项通过。Python 3.12.14 与 3.11.18 的语音/协议/动作相关回归各 51 项通过；[试用 Qt 集成](../tests/test_assistant_trial_qt.py)另复现并修复排队成功覆盖停止，不替代实体音频验收。

## 29. 试用请求应复用执行链并隔离业务上下文

- **改了什么：** 试聊使用现有受限流式 HTTP 与取消 worker，但仅发送固定问候；试听使用现有真实 TTS 驱动播放固定短句。试聊结果只在独立窗口显示。
- **为什么：** 用户可以检查实际模型和音频链路，同时保留正在编辑的问题、审批附件、上一回复与普通历史。
- **踩坑：** 直接调用“发送”按钮会消费业务上下文；另写传输则容易丢掉已有取消和本地地址边界。独立窗口的缺配置提示也必须出现在前景，不能只更新被遮住的主助手。
- **验证：** [实际 Qt/回环 HTTP 集成](../tests/test_assistant_trial_qt.py)检查真实请求只含系统与固定用户消息，不携带 PPL、记忆或附件，不写历史；模型/地址往返修改、关闭、角色切换及缺配置提示均有回归。

## 30. 诊断报告从白名单构建，未知值不能写成失败

- **改了什么：** 最近 30 条记录只接收固定枚举、布尔值和数字；导出重新构造字段白名单。异常仅传类别和受限观测元数据。
- **为什么：** 提示词、回复、转写、路径、原始模型 ID 和异常正文可能含私人信息，不能靠导出时逐个删除敏感键来保证遗漏字段安全。
- **踩坑：** `speak_interruptible` 的 False 表示用户停止，可能根本没收到驱动完成回调；这时 `engine_completed` 应为 null。只有实际回调布尔值才能成为证据，驱动明确未完成的 False 通过 `VoiceUnavailable` 结构化元数据传递。
- **验证：** [记录器测试](../tests/test_assistant_trial_records.py)覆盖任意额外字段、非有限数字和元数据筛选；[Qt 集成](../tests/test_assistant_trial_qt.py)检查秘密哨兵不进入报告，并区分准备阶段停止与实际驱动负值。程序成功与三组人工反馈始终分离。

## 31. 已预览报告要冻结，导出失败只影响导出

- **改了什么：** 实时记录与用户已预览快照分别保存；导出使用固定快照和独占创建，拒绝覆盖，失败仅在诊断窗口反馈。
- **为什么：** 用户在保存对话框中选择路径时，后台聊天/监听仍可能继续，保存内容必须与此前展示的报告相符。
- **踩坑：** 后台刷新不能悄悄更新已审核数据；清空记录也要清掉冻结预览。导出失败不能走主任务的错误清理分支，否则会误停音频或撤销停止按钮。
- **验证：** [诊断窗口 Qt 测试](../tests/test_assistant_trial_dialog_qt.py)验证冻结/更新、取消、失败重试、拒绝已有文件及清空；[集成测试](../tests/test_assistant_trial_qt.py)验证导出失败、关闭诊断窗口后主助手监听仍可正常停止。

## 32. 资源采样要明确范围并控制自己的开销

- **改了什么：** 标准库采样桌宠进程 CPU 与当前 RSS，活动中通常每秒一次，开始/结束额外采样；只报告采样最大内存，不把缺失值写成零。
- **为什么：** 模型服务是另一个进程，桌宠 CPU 不等于模型 CPU/GPU，采样值也不能证明瞬时峰值或长期稳定性。
- **踩坑：** Windows 每次采样重新定义 ctypes 结构，会被 POINTER 类型缓存保留，诊断本身反而持续占内存；应复用结构类型。Linux 的驻留页数需要乘页大小，不能把页数当字节。
- **验证：** [记录器测试](../tests/test_assistant_trial_records.py)在实际 Python 3.9.25 / 3.11.18 / 3.12.14 各 21 项通过，覆盖 CPU 算术、RSS 单位、不可用数据和 Windows 重复类型缓存。原生 Windows 调用仍由对应平台执行确认。

## 33. Qt 测试替身不能把窗口带入后台垃圾回收

- **改了什么：** 文件夹授权用例的四个纯返回选择器，使用不保留调用记录的函数替身；保留原授权拒绝/接受、文件创建和重置断言。
- **为什么：** Qt 6.8 全量出现 exit 139，而 Qt 6.5 通过。缩到 61 项固定序列并追踪后，发现最后一个 Qt 用例的 MagicMock 调用记录保留了父窗口，稍后在 HTTP 工作线程的 GC 中才释放 wrapper，下一次 Qt 事件循环崩溃。
- **踩坑：** close() 不保证销毁 Qt 对象；单测单独通过也不证明跨测试生命周期正确。为了只返回固定选项而引入带自引用/调用记录的替身，会改变 GUI 对象释放线程。
- **验证：** 修正前追踪显示窗口在 WORKER 线程回收；修正后原顺序 61 项通过，追踪确认窗口在自己的用例结束时于 MAIN 线程释放和销毁。未关闭 GC、改测试顺序、跳过断言或修改生产逻辑；最终全量结果见本批验证记录。
- **本批补证：** 语音设置扩展后的 Python 3.9 全量在后续 HTTP 测试原生崩溃。原 Qt/HTTP 顺序 48 项自然执行通过，在首个真实 HTTP handler 中仅增加一次诊断 GC 后退出 139；追踪指出 `_submit` Mock 保存的 `_speech_completed` 绑定方法仍持有语音失败测试窗口。只给该 Qt 夹具增加 GUI 线程显式销毁后，原顺序与相同压力各 48 项通过，原生窗口树先在 MAIN 销毁，之后 WORKER 释放 wrapper 已无原生对象。原全量没有 GC 探针，因此不把这个对照说成已捕获原崩溃的确切回收时刻，详见 [语音控制验证](verification/2026-11-18-voice-controls.md)。

## 34. 复杂 Qt 夹具要明确销毁，不能依赖下一次垃圾回收

- **改了什么：** 任务整合测试增加专用清理：关闭窗口，等待仍在运行的 worker 结束，再于 GUI 线程执行 `deleteLater()` 和 `DeferredDelete`。完整 CI 命令启用 `-X faulthandler`，保留全部测试和原顺序。
- **为什么：** 提交 `1020d9f` 的 [Windows / Python 3.9 完整回归](https://github.com/clonetimer/DyberPet/actions/runs/44253642180/job/134630027117)在下一个任务窗口测试直接退出，没有断言栈。前序任务整合夹具仍通过 Mock 调用记录和回调持有已关闭窗口，单纯替换个别固定返回替身不足以覆盖复杂夹具。
- **踩坑：** 在真实 Python 3.9 / Qt 6.5 的原顺序 50 项中，让随后真实 HTTP 回调执行一次 GC，观察到前序窗口 wrapper 在 WORKER 回收，接着在与远端相同的测试 `app.processEvents()` 崩溃。只改变前序清理后，原生 Qt 对象先在 MAIN 销毁，之后 WORKER 回收 wrapper 不再崩溃。原远端没有原生栈，因此该对照证明生命周期漏洞，不把人为触发的 GC 说成远端已捕获的根因。
- **验证：** 修正后的原顺序 50 项与相同 HTTP GC 压力序列均全部通过；[夹具修复](../tests/test_assistant_task_integration_qt.py)没有关闭 GC、重排测试、替换所有 Mock 或改变产品行为。完整回归与修复后精确 SHA 的远端结果继续记录在 [验证记录](verification/2026-11-18-assistant-trial-diagnostics.md)和 PR。

## 35. 一句话捕获与连续听写需要不同的停止语义

- **改了什么：** 新增每轮只接收首个非空完整语句的识别器，同场缓存 Vosk Model，每轮独立创建 recognizer 和音频流；停止返回空串，关闭流后再次检查停止。
- **为什么：** 连续听写的停止会收尾并保留文本；语音会话的结束必须丢弃尚未提交的内容，否则用户结束后仍可能收到回答。
- **踩坑：** 从 `with` 内直接 return 会先计算返回值，再关闭流，关闭期间的停止可能遗漏。sounddevice 在构造时创建流、`__enter__` 时启动，启动失败不会执行 `__exit__`，必须为已创建但未关闭的流保留 finally 清理；依据为 [官方实现](https://python-sounddevice.readthedocs.io/en/latest/_modules/sounddevice.html)。
- **验证：** [识别器回归](../tests/test_assistant_voice_turn.py)先观察缺失实现、无效音频和启动失败等失败，再修复为 33 项通过；与既有语音测试合计 78 项在 Python 3.9/3.11/3.12 各通过。受控驱动验证生命周期，不证明实体麦克风准确度。

## 36. 自动接续必须使用线程结束边界，并恢复阶段间的控件

- **改了什么：** 独立 VoiceConversation 在成功回调只暂存下一阶段，等宿主清理 worker 后再通过单次事件推进；每次推进重验会话代次、角色、配置与窗口状态。结束撤销所有后继，打断等旧任务退出后重新听。
- **为什么：** 固定等待 100ms 不能保证识别、HTTP 或 TTS 已退出；复用单 worker 才能避免边朗读边录入自身声音。
- **踩坑：** 阶段之间虽然没有 worker，会话仍在占用控件。恰在 finished 后结束时，若只靠 worker 清理恢复按钮，按钮会被活动会话再次禁用后永久保留。控件状态应从“会话或 worker 是否忙碌”重新计算，试用窗口同步收敛。
- **验证：** [实际 Qt/HTTP 集成](../tests/test_assistant_voice_session_qt.py)复现“发送”按钮未恢复，再修复；还执行两轮往返、排队成功后停止、生成/朗读打断、配置和角色变化、关闭、失败、20 轮和定时结束。音频边界受控，Qt 线程、HTTP 客户端与历史存储保持真实。

## 37. 自动语音聊天不能通过点击听写和发送按钮拼接

- **改了什么：** 从手动发送提取共享聊天入口；语音显式传入识别文字，复用角色历史、批准记忆和 PPL，保留输入框与待手动发送附件。语音成功只排一次 TTS，普通自动朗读不再重复排队。
- **为什么：** 用户可以一边保留草稿，一边与桌宠说话；尚未手动发送的文件不能被下一句语音顺带带走。
- **踩坑：** 普通失败/取消逻辑会把请求文字恢复到空输入框；语音轮次不能复用这份键盘重试文本。语音与手动 auto_speak 同时开启时，也不能产生两次播报。
- **验证：** 两轮真实 HTTP 请求含既有历史与上一轮回答，不含待发送附件哨兵；草稿/附件原样保留，成功历史完整，播报次数恰为两次，工作区无文件生成。

## 38. 原生状态动作的声音与占用判断要沿真实运行路径

- **改了什么：** 听/想状态只选择已加载、已解锁且无声的原生 random_act；缺少合适动作时使用原气泡。保留拖拽、跟随、坠落、专注、固定动作、已有交互及暂停/停止动画的优先级。
- **为什么：** 菜单的 allAct_params 只有动作/解锁元数据，实际播放音效由 PetConfig.act_sound 决定。用菜单中不存在的 sound 字段判断，会把有声动作当成无声动作，可能被麦克风重新识别。
- **踩坑：** 没有当前交互不等于动画可以被接管，Animation worker 仍可能暂停或停止；无帧、空图像和无效帧时长同样不能自动播放。附属和 customized 动作没有在此路径证明可安全自动调度，因此沿原气泡回退。
- **验证：** [原生反馈测试](../tests/test_assistant_interaction_sync.py)执行实际 PetWidget 与 Interaction_worker 方法，验证选帧、完成和回退；资源无效与动画暂停分支均先观察失败后修复。16 项全部执行，不靠源代码字符串断言。

## 39. 异步测试要等待用户实际可见的状态

- **改了什么：** 生成中断测试在 HTTP 已写入数据之外，继续等待 Qt 文本框实际出现增量，再点击打断。
- **为什么：** 该用例验证“已经显示的部分回复保留、不写历史”，服务器 flush 只证明发送端已交付数据，不能证明 GUI 已消费 queued signal。
- **踩坑：** 单模块通过而整批一次失败，日志显示取消正确生效，但尚未显示的增量被拒绝。不能为此放行取消后的迟到增量；应修正测试的同步边界。
- **验证：** 保留真实本地 HTTP 和 QThread，只改变等待谓词；不添加任意延时或放宽断言。与阶段恢复修复一起完成 14 项 Qt 集成，完整结果见 [本批验证记录](verification/2026-11-18-voice-conversation.md)。

## 40. 持续语音的停止入口应留在可见区域

- **改了什么：** 将同一组开始、打断、结束和阶段标签放到滚动内容外的固定顶部；其他设置和历史继续滚动。
- **为什么：** 用户读较低位置的回复时仍需立即结束麦克风或打断朗读，不能为了控制正在进行的会话先滚回窗口顶部。
- **踩坑：** 顶部初始截图看不出问题；第二张朗读截图显示按钮已滚出视口。按钮存在且 enabled 不等于它在用户当前可见区域内。
- **验证：** 800×600 的真实 Qt 窗口滚到底部，按映射后的实际控件矩形断言，先复现按钮在视口之外，再验证固定布局通过。两张实际 800×800 截图同步更新；独立审阅另运行该回归确认。

## 41. Qt 测试等待还必须让 Python 工作线程获得执行时间

- **改了什么：** 语音 Qt 测试改为处理 GUI 事件后短暂 `time.sleep` 让出 GIL，保留原 3 秒/5 秒超时；第三次监听显式等待界面接收 ready，后台回复门闩仅由测试或无条件清理释放。超时附当前任务/轮次快照。
- **为什么：** `e97ec6c` 的 Windows Qt 和完整矩阵出现打断恢复、20 轮结束与最后 listening 状态失败，Linux 三套完整通过不能替代该平台证据。Qt 6.5 下的实测显示 `qWait(500)` 期间 Python 线程仅推进一次，GUI 等待本身压制了需要被等待的 Python HTTP/音频任务。
- **踩坑：** 将线程切换间隔临时设为 50ms，原 20 轮用例在相同 5 秒上限时只推进到 7 次监听/6 次朗读而失败，协作等待则约 0.85 秒完成 20 轮。仅给第三轮 ready 前加入 20ms 准备，原固定 130ms 等待就复现远端完全相同的缺尾状态，显式等 Qt ready 后通过。工作线程计数不是 GUI 已就绪的证据。
- **验证：** 修复后原 15 项及相同调度压力下的 3 项均通过，不放宽断言、不增加超时、不改产品取消行为。未在本地精确复现 Windows 的取消超时，因此将 GIL 观测、两项确定性对照和新 SHA 的原 Windows 门禁分别记录，不把推断写成远端已捕获的根因。

## 42. 客户端取消不能依赖服务端帮忙关闭响应

- **改了什么：** 为现有本机 HTTP 响应添加可检查取消的原始读取层；等待数据时以最多 100ms 的片段轮询，保留真实 SocketIO 的引用生命周期、HTTP 解析/缓冲、原读取超时与 worker 清理。请求写入路径保持原超时方式。
- **为什么：** `270e40c` 已在 Windows 修复前两项时序用例，却仍在三个作业中稳定出现“打断后旧 chat worker 运行中”。沿实际 UI→token→socket 追踪未发现漏取消；旧 HTTP 测试服务收到客户端 FIN 后立即关连接，会替客户端完成唤醒，没覆盖保持连接但不继续返回的服务。
- **踩坑：** 不能在 `HTTPResponse.readline()` 外捕获短超时再重试；实际 SocketIO 超时后下一次读取会报“cannot read from timed out object”。应在缓冲层之下等待可读性，避免短轮询破坏完整 SSE 行、HTTP chunk 和 JSON。跨线程关闭缓冲 reader 则可能等待其读锁，清理仍应留在 worker。
- **验证：** 真实回环服务分别保持响应头、SSE、JSON 等待，仅将 OS shutdown 唤醒边界替为无效果，三种原实现均失败；修复后全部通过。新增碎片/150ms 间隔、HTTP chunk 与原超时回归，15 项请求合约和 15 项语音 Qt 集成通过；独立追踪确认用例清理前所有客户端句柄和 token 注册均已释放，同一无唤醒条件下的真实 Qt 打断也通过原 3 秒断言。三套完整 865 项各 860 通过、5 既有环境跳过。最终 Windows 结果按新提交核验，不把 Linux 探针当成 Windows 原生堆栈证据。

## 43. 设备目录可以部分展示，但唯一匹配必须完整

- **改了什么：** 麦克风保存精确设备名与 host API 名，每次捕获重新解析当前索引；默认、缺失和歧义分别处理。设备与系统音色目录由 worker 显式读取，只返回不可变元数据。
- **为什么：** 数字索引会随设备顺序变化，同名设备也可能来自多个音频接口；保存索引或模糊匹配可能把另一支麦克风当成用户原选择。
- **踩坑：** 首版解析跳过坏元数据后，另一个坏条目恰好可能是同名设备，剩余条目就被错误判定为唯一。目录展示可以附警告保留有效项，使用时遇到不完整目录则必须拒绝匹配。库目录刷新也不等于完整 USB 热插拔支持。
- **验证：** [设备目录回归](../tests/test_assistant_voice_devices.py)先观察组件缺失，以及坏条目隐藏重复身份的失败，再修复为 34 项通过；没有录音、播放、Vosk 加载或私有 PortAudio 重初始化。

## 44. 音频选择要贯穿角色、入口与异步生命周期

- **改了什么：** 麦克风全局保存，系统音色/语速按角色保存；旧配置使用默认值，缺失的已保存选择保留并标为不可用。试听、手动/自动朗读共享设置快照，改变音频配置撤销旧音频结果与进度。
- **为什么：** 只增加下拉框会让设置看起来有效，却在另一种入口仍用默认设备；切换角色时也不能把上一角色的声音悄悄带过去。
- **踩坑：** 宿主 `_submit` 已把 `on_progress` 用作流式 UI 路由，直接把同名关键字传给 TTS 会被宿主截走。真实 Qt 回归先报“缺少 on_progress”，随后把播放回调绑定到任务本身，保持两条进度通道的含义。
- **验证：** 设置持久化 13 项通过，新增实际 Qt 设置集成 11 项通过，覆盖无自动驱动导入、worker 刷新、角色保存恢复、旧结果拒绝和各播放入口参数。驱动效果由后续生产播放/捕获回归另验，不把 UI 参数传递当成实机音频效果。

## 45. TTS 属性设置也在队列中，播放前必须确认成功

- **改了什么：** 先连接驱动 error 与命名完成事件，再排音色/语速设置并驱动外部循环；确认队列处理及选中音色生效后才排第一段。所有驱动对象仍由同一 worker 创建、使用和清理。
- **为什么：** pyttsx3 的 `setProperty` 并不保证调用时已执行。属性失败可能被驱动队列捕获并作为 error 事件发出；提前把 say 放在后面，会让错误配置之后的默认声音继续播放。
- **踩坑：** 在 error 回调中直接抛异常也可能被引擎吞掉。回调应只记录状态，由工作循环决定失败；显式音色失效不得静默回落到默认音色。参考 [引擎 API](https://pyttsx3.readthedocs.io/en/latest/engine.html) 与 [v2.99 队列实现](https://github.com/nateshmbhat/pyttsx3/blob/v2.99/pyttsx3/driver.py)。
- **验证：** [完整播放回归](../tests/test_assistant_speech_output.py)的受控驱动按真实排队语义执行，覆盖属性错误、属性 readback 不一致、取消准备和零 say 断言；26 项与既有语音生命周期/人格测试合计 71 项在 Python 3.9/3.11 均通过。

## 46. 一段完成不能代表整条回复完成

- **改了什么：** 最多 2000 字符保留原文顺序，分成每段最多 500 字符；每段使用本次调用唯一的名称，完成后才排下一段。全程一个引擎、一个 ready、一个含准备时间的 300 秒期限，进度只传段数。
- **为什么：** 原逻辑确实只读了 2000 字符中的前 500 字符。多段处理还会引入旧完成事件、停止边界和前缀误判，不能只把原 `say` 调用放进循环。
- **踩坑：** 第一段完成后第二段失败时，旧的 True 元数据曾被误记为整条完成；新增回归先分别复现驱动失败与进度回调失败，再只保留实际最后一段的 True。错误名称、重复与迟到完成均不能推进，停止会撤销后续段落。
- **验证：** [真实 Qt 会话](../tests/test_assistant_voice_session_qt.py)贯穿回环 HTTP 与生产播放循环，仅替代物理驱动；1200 字符三段播放、第二段停止、第二段失败均通过，最后一段及线程清理前不会再次开麦。该结果证明编排和文本完整性，不证明实体扬声器已发声。

## 47. 选定输入设备不能改变捕获资源的所有权

- **改了什么：** 兼容单次识别、手动连续听写和轮流对话均在模型准备后、创建流前解析设备，默认设备不额外枚举；构造出的流在启动异常或随后取消时也显式关闭。
- **为什么：** sounddevice 的流在构造时已占有资源，`__enter__` 才启动；启动抛异常时 Python 不会调用 `__exit__`。设备选择增加的新等待边界也要重查停止，避免已取消任务仍开麦。
- **踩坑：** 三种入口的结束语义不同：手动听写允许停止后收尾文字，轮流对话必须丢弃未发送语句。共用设备解析可以复用，不能顺手统一这两种业务语义。
- **验证：** [设备选择捕获回归](../tests/test_assistant_microphone_selection.py)17 项通过，覆盖重新编号、缺失/歧义、默认行为、构造后停止和启动失败清理；保留原识别器 33 项及旧听写断言。

## 48. 真实驱动忽略的输入不能等待完成回调

- **改了什么：** 文本分段仍保留全部原文；在交给 TTS 前排除完全由空白组成的段，进度只统计可播报段，非空段保持原文与顺序。
- **为什么：** 独立审阅用 pyttsx3 2.99 的实际 `Engine.say` 方法复现：500 字正文、两个换行、500 字正文会产生空白中间段，而引擎直接忽略它、不发完成事件；原播放循环会等待到总超时。
- **踩坑：** 仅校验分段拼回原文是不够的，测试驱动也必须体现输入被忽略的语义。超过 500 个连续空白时，不可能让每个保真且不超限的片段都有正文，因此在播放边界跳过无声段比删改原文更明确。
- **验证：** 中间、开头、结尾与超长空白的四个回归场景先实际超时，修复后完整播放和清理通过；播放及既有语音回归共 72 项在 Python 3.9 通过。独立审阅使用固定版本实际方法再次复核四种场景，均通过。

## 49. 尚未启动的自动朗读也必须能够撤销

- **改了什么：** 普通回复的延后朗读改由窗口持有的单次 QTimer 调度；音频设置变化、切换范围、切换自动朗读开关或启动新操作都会停止待执行计时器。已显示回复仍可手动朗读。
- **为什么：** 原静态 `singleShot` 已排队但 worker 还不存在时，活动任务取消逻辑不会命中；语速从 A 改到 B 再改回 A，旧回复仍会自动播放。配置值相等不代表这段期间没有发生撤销。
- **踩坑：** 会话控制器的下一阶段已有代次校验，不能据此推断普通 auto-read 也受保护。需要沿实际入口检查尚未进入 worker 的工作。
- **验证：** [实际 Qt 设置测试](../tests/test_assistant_audio_settings_qt.py)先观察 A→B→A 后仍发生播放，再修复；还验证原文保留且能手动读、配置未变时仍自动读一次。设置 Qt 集成由 11 项增至 13 项，全部通过。

## 后续更新方式

只在出现新的可复用判断时增加条目。每条保留“问题 → 原因 → 实践 → 验证”，并链接实现、测试或实际运行。新的绿色基线单独记录完整 SHA 与运行结果；未运行的测试、被跳过的依赖及尚缺的实机证据明确写出。已有功能列表和面向用户的操作说明继续维护在各自文档中。


## 50. Linux eSpeak 的外部事件循环不能假定与 Windows/macOS 一致

- **改了什么：** Linux 朗读切换为 eSpeak NG 子进程后端，UTF-8 文本只通过 stdin 传递；每段子进程由当前语音 worker 创建、等待和清理，停止/总时限通过 terminate/kill 作用于本次进程。Windows/macOS 保持 pyttsx3 路径。Linux 被动就绪检查现在同时要求 pyttsx3 音色目录和 `espeak-ng` 命令。
- **为什么：** 固定版 pyttsx3 2.99 的 eSpeak 驱动 `iterate()` 返回 None，`DriverProxy` 外部循环却执行 `next(iterator)`；改用驱动内循环虽绕过该异常，但其合成回调会同步调用系统播放器，无法由应用可靠控制播放子进程。Linux 需要独立、可终止的播放进程，而不是把“调用返回”误当成“可以中断”。
- **踩坑：** `espeak-ng --stdin` 会一直读取到 EOF，因此每个有界文本段要写完并关闭 stdin；不能把用户文本放入命令行参数或 shell 字符串。进程返回码为 0 才能计入该段完成，停止/超时必须终止当前进程且不能启动后续段。便携包不包含系统 eSpeak NG 可执行文件，必须明确提示安装系统依赖。
- **验证：** 新增 Linux 子进程合约测试覆盖 UTF-8 分段、音色/语速参数、单次 ready、分段进度、停止时终止当前进程、非零退出和缺少可执行文件；Linux X11 工作流安装 eSpeak NG 并运行合约测试与真实合成 WAV 冒烟。此自动化不证明实体扬声器可听效果，仍需用户实机试听。


## 51. 后端切换后，测试夹具必须声明它模拟的操作系统

- **改了什么：** 对仍然模拟 pyttsx3 驱动生命周期的语音、试用窗口和轮流对话测试，显式将被测平台设为 Windows；Linux 专项测试则显式设为 Linux 并模拟 eSpeak NG 子进程。被动就绪测试为“系统命令是否存在”提供独立受控条件。
- **为什么：** 生产代码现在按平台选择不同后端。旧测试只注入一个假的 pyttsx3 模块，却默认当前 CI 平台仍会走 pyttsx3；在 Ubuntu 上，这种测试实际上会进入 eSpeak NG 分支，导致它等待一个永远不会触发的假驱动初始化事件。
- **踩坑：** 只注入模块不等于模拟平台；测试还必须固定平台分支和系统可执行文件发现结果。反过来，不能把所有 Linux 测试都强制模拟 Windows，否则会让真正的 Linux 后端永远不执行。
- **验证：** Linux/Windows Python 3.9、3.11 全量回归均执行真实的分支选择；Linux 专项子进程测试独立验证停止和分段。修复仅调整测试夹具，没有放宽产品行为或跳过测试。


## 52. Linux 音色目录与 CLI 后端必须做逐项兼容验证

- **改了什么：** Linux X11 工作流新增真实音色兼容性测试：从 pyttsx3/eSpeak 驱动读取系统音色 ID，再逐项通过 eSpeak NG CLI 的 `-v` 参数合成临时 WAV；不连接实体扬声器、不写入用户目录。
- **为什么：** “pyttsx3 能枚举音色”与“同一音色 ID 能被新 CLI 后端接受”是两个独立契约。只用默认音色做合成冒烟，不能证明设置面板列出的每一个可选音色都能播放。
- **踩坑：** 不应手工维护一份假设性的音色名称清单；直接读取当前 CI 系统的真实目录，再逐项调用 CLI，能捕获命名映射和版本差异。测试仍不证明中文发音质量或真实声卡输出。
- **验证：** Linux CI 使用当前安装的 eSpeak NG 数据目录，要求音色目录至少包含两个可用 ID；每个 ID 均须在 10 秒内成功生成非空 WAV。2026-11-18 的 Linux X11 CI 从真实 pyttsx3/eSpeak 目录枚举到 131 个 ID，全部在 1.071 秒内通过，包含普通话 `cmn`、拼音 `cmn-latn-pinyin`、粤语 `yue` 与拼音 `yue-latn-jyutping`。结果以最终 Linux 工作流为准。


## 53. 可选平台集成测试不能在模块导入阶段要求可选依赖

- **改了什么：** Linux 音色目录兼容测试将 `pyttsx3` 延迟到测试体内导入，并在非 Linux 平台跳过；通用助手单测环境未安装该可选依赖时，也只跳过这项集成测试。Linux 专用 X11 工作流仍安装完整音频依赖并显式运行该测试，因此 Linux 门禁不会把缺少依赖误报为通过。
- **为什么：** unittest discovery 会在所有平台导入 `tests/` 下的模块。即使工作流仅在 Linux acceptance job 中显式执行新测试，助手通用全量套件仍会发现它；模块顶层导入 `pyttsx3` 会让不安装可选音频依赖的环境在测试执行前直接失败。
- **踩坑：** 平台专用测试应在模块导入时只依赖标准库；平台和可选依赖检查放在测试方法内部。使用 `skipTest` 仅用于不具备该集成环境的通用套件，不能在专用 Linux acceptance job 中跳过。
- **验证：** Ubuntu/Windows Python 3.9/3.11 通用助手套件重新运行；Linux X11 acceptance 单独执行真实 pyttsx3 音色目录到 eSpeak NG CLI 的逐项 WAV 合成验证。以最新 CI 结果记录通过数和实际音色数。


## 54. 子进程取消需要验证 terminate 超时后的 kill 兜底

- **改了什么：** 为 Linux eSpeak NG 子进程补充“忽略 terminate”的故障注入测试，确认工作线程在短等待窗口结束后升级为 kill，并且不会启动下一段语音。
- **为什么：** 正常停止测试只证明协作式子进程会退出；系统音频后端卡死或子进程处于不可及时响应状态时，单独调用 terminate 并不构成有界取消保证。
- **踩坑：** 不能只断言 stop_event 被置位，也不能只断言 terminate 被调用；必须模拟子进程忽略 terminate，检查 kill 确实发生并最终 wait 回收。
- **验证：** 新增 Linux 进程合约测试，检查 terminate 超时后 kill 升级、当前子进程回收、后续语音段不启动；由 Linux X11 acceptance job 执行。
