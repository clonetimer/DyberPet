## 1. 文件正文要保持资料身份

- **问题：** 用户选择了一个文件，不代表同意执行文件内的指令。把正文拼进系统提示词，会把资料和应用规则混在一起。
- **原因：** 文件属于外部输入，可能含有角色声明、要求泄露信息的文字或伪造分隔符；用户批准的是读取指定资料。
- **实践：** 系统层仅保留“按不可信资料处理”的规则；文件名、正文及分隔符放在独立 `user` 消息中，真正的问题放在其后。模型输出仍只作为文本，不能因此获得文件动作权限。长度、UTF-8 和请求体角色结构都要校验，不能只靠提示词。
- **验证：** 检查 [persona.py](../DyberPet/assistant/persona.py) 的 `stream_local_chat`；[协议测试](../tests/test_assistant_persona_voice.py) 中 `test_local_stream_includes_user_approved_file_as_untrusted_reference` 验证请求角色与恶意正文位置，`test_local_stream_rejects_invalid_file_context` 验证上限。该测试证明请求结构，不证明模型绝不会受提示注入影响。

## 2. 审批应绑定内容与一次具体动作

- **问题：** 用户确认后，同一路径的文件可能已经变更；旧审批也可能被重复使用或带到另一个工作目录。
- **原因：** 路径名称不是内容身份，长期布尔授权也不能表达“此刻、此目标、此动作”。
- **实践：** `prepare → approve → execute` 分阶段；读取审批绑定文件字节 SHA-256，执行前复核；动作使用白名单、精确目标、短有效期和一次性请求 ID。工作区切换清空待执行审批。日志只保留动作、目标、状态和必要错误信息，不记录文件正文。若动作已成功但最后一条审计写入失败，返回成功及审计警告，避免诱发重复执行。
- **验证：** 查看 [action_runtime.py](../DyberPet/assistant/action_runtime.py) 及 [动作测试](../tests/test_assistant_action_runtime.py)：覆盖确认前阻断、拒绝、过期、重复使用、内容变更、工作区切换、恢复冲突和正文不写审计。SHA-256 校验不等于文件系统操作已经获得完整的抗竞争保证；新增并发路径要单独审查检查与使用之间的窗口。

## 3. 会话资料必须有明确生命周期

- **问题：** 附件、角色人设、识别结果或模型回复可能在角色切换、工作区撤销、窗口关闭后继续使用。
- **原因：** 异步任务持有启动时的快照，清空界面字段并不能撤销已发出的请求或阻止迟到回调。
- **实践：** 为任务记录角色和会话代次，接收增量和最终结果时核对身份。附件仅供下一次成功请求，成功后清除；网络失败保留待用户重试；角色、工作区或窗口生命周期变化时清除待用上下文。修改这些入口时，同时检查在途任务、迟到回复、缓存、审批和历史，不能只检查一个字段。
- **验证：** 查看 [ui.py](../DyberPet/assistant/ui.py) 的 `set_character`、`send_message`、`_message_reply`、`reset_workspace` 和 `closeEvent`；[Qt 测试](../tests/test_assistant_qt.py) 已覆盖单轮附件消费、角色隔离、工作区重置及旧角色增量丢弃。文件任务草案批次之前，工作区重置只清附件；`9945a31` 通过统一会话失效入口补齐，并在 [任务集成测试](../tests/test_assistant_task_integration_qt.py) 中验证迟到成功、错误和麦克风部分转写；不能由“清空字段”推定安全。

附件原文不作为独立历史条目保存，不等于原文绝不落盘：模型回答可能引用资料，而已完成回答会进入本地会话历史。涉及隐私说明或历史策略的修改，应同时检查 [conversation_store.py](../DyberPet/assistant/conversation_store.py) 和 `_message_reply`。

## 4. 线程结束、收到文本与业务成功要分别处理

- **问题：** 收到部分流式文本后断线，界面可能误报完成；关闭窗口时仍在运行的语音线程可能被提前销毁；UI 直接停止语音驱动还可能违反线程归属。
- **原因：** 增量事件、任务结果、`QThread.finished` 和驱动回调具有不同含义，不能共用一个“完成”状态。
- **实践：** UI 只更新控件或设置停止事件，TTS 引擎由创建它的工作线程初始化、迭代和停止。保留线程对象直至 `finished` 再清理。窗口先请求停止并等待完成通知。流式协议至少要求收到 `[DONE]`；断流保留已显示文字并标明中断，不把它写成成功的一轮，也不自动播报或保存为便签。业务成功、协议结束和线程释放分别决定各自的后续动作。
- **验证：** 查看 [voice.py](../DyberPet/assistant/voice.py) 的 `speak_interruptible`、[ui.py](../DyberPet/assistant/ui.py) 的 `_submit`、`_job_finished`、`closeEvent` 和 [persona.py](../DyberPet/assistant/persona.py) 的 SSE 解析。回归入口是 [语音/协议测试](../tests/test_assistant_persona_voice.py) 中断流与可中断 TTS 用例，以及 [Qt 测试](../tests/test_assistant_qt.py) 中窗口等待、旧角色结果丢弃和中断标记用例。模拟驱动通过只能证明控制流程，不能证明真实设备的可听效果与停止延迟。

## 5. 先在本地完成一个改动，再原子提交

- **问题：** 远端逐行改文件容易产生修复提交连锁，也容易把真实换行写成字面量 `\\n`。
- **原因：** 内容在 shell、JSON、脚本和目标源码之间经过多次编码，修补时又缺少完整文件和请求体检查。
- **实践：** 在本地工作副本一次完成相关代码、测试和说明；尽量通过补丁或文件参数传递文本。检查实际 diff 和最终字符串，再跑针对性回归，最后按一个完整行为提交。提交消息描述问题和变化，避免用多次小提交代替本地验证。
- **验证：** 历史提交 [`541dae2`](https://github.com/clonetimer/DyberPet/commit/541dae2bd417852bda1d48b1e6d19608c8cd6032) 的主题是修正文件上下文分隔符为真实换行；随后文件任务草案批次在现有聊天协议测试和任务规划 HTTP 测试中补充真实换行断言。提交前执行 `git diff --check`、检查 `git diff`，并运行影响范围内的测试。浅克隆只显示当前提交时，不凭空补写更早的提交顺序或根因证据。

## 6. 等待 CI 时按一批结果作判断

- **问题：** 每隔几秒查询同一工作流，消耗时间但不能缩短 Windows 打包；不同 SHA 的绿色结果也容易被混用。
- **原因：** 把“仍在运行”当成新证据，或只记录分支名和页面上的绿色图标。
- **实践：** 一次提交后记录完整 SHA，集中取得该 SHA 的相关运行；让独立作业并行，按有意义的间隔查询整批状态。出现失败才读取相应作业日志。检查工作流的分支与路径过滤：文档变更未触发工作流时，记录“未运行”，不能补写“通过”。产物同时记录运行 ID、artifact ID、大小、摘要和保留期。
- **验证：** [桌宠工作流](../.github/workflows/pet-assistant.yml) 有 4 个系统/Python 单测组合、1 个 Qt 作业、1 个 PPL 合约作业；[Windows 工作流](../.github/workflows/windows-portable.yml) 单独构建并启动冻结 EXE。最终记录应核对运行所属 SHA 与全部必要作业结论，不能拿上面的旧绿色基线代替本轮结果。

本批额外触发的 [角色导入工作流](../.github/workflows/character-mod-importer.yml) 还暴露了镜像漂移：`ubuntu-latest` 已解析到 Ubuntu 26.04，`setup-python` 找不到 Python 3.9。该矩阵改为 `ubuntu-24.04`，保留 Python 3.9/3.11 覆盖；这种失败应修正环境契约，不能删掉版本检查来取得绿色。

## 7. 验收结论按证据层级书写

- **问题：** 单测、离屏 GUI、打包后 EXE、真实设备和性能验收混写，会让“能导入模块”看起来像“完整体验已可用”。
- **原因：** 测试名称相近，但执行环境、替身依赖、真实输入和观测指标不同。
- **实践：** 每项结论写清版本、环境、实际执行对象与覆盖边界。性能工作先确定测量流程与指标，再采样；至少区分首段回复延迟、完整回复延迟、麦克风停止延迟、TTS 停止延迟、CPU/内存和长时间运行趋势。没有真实模型与设备数据，就保留为待验收项，不编造数值或达标结论。
- **验证：** Windows 流程确实从其他工作目录启动 `DyberPet.exe --assistant-smoke`，但 Qt 使用离屏模式，语音组件主要检查打包与导入。实机验收另需记录模型 ID、量化/配置、硬件、驱动、样本和可复现操作。详见 [Windows 验收边界](windows_portable.md) 和 [助手自动化边界](pet_assistant.md)。

## 8. 严格解析必须覆盖整个模型响应

- **问题：** 内层任务 JSON 校验再严格，外层 HTTP JSON 如果有重复的 `finish_reason`、`content`，普通解码器已经丢掉了歧义。空字典也可能被真假值检查误判为“没有工具调用”。
- **原因：** 安全判断发生在解析之后；宽松解析无法把原始歧义交给后续校验。
- **实践：** 任务专用解码器从外层开始拒绝重复字段、非有限数值和过深嵌套；控制字段校验类型，只接受完整 `stop` 回复。草案是不可变数据，审批 token 由本机生成。
- **验证：** [任务规划测试](../tests/test_assistant_task_planner.py) 使用真实回环 HTTP 服务器重现重复完成原因、重复内容、畸形 `tool_calls` 和 `refusal`；修复前接受这些响应，修复后全部拒绝。正常聊天无需跟随任务协议改变。

## 9. 窗口关闭要覆盖 Esc 与真实事件循环

- **问题：** `QDialog` 按 Esc 可以隐藏父窗口而绕过原有 `closeEvent`，留下可批准的任务子窗口；只直接调用方法的测试发现不了这条路径。
- **原因：** `reject()`、窗口关闭事件和线程结束是不同入口。延迟删除子窗口又与父对象销毁交织，可能在后续事件循环中暴露生命周期错误。
- **实践：** Esc 与关闭按钮统一撤销 scope，停止语音并等待 worker；避免 `closeEvent → reject → close` 递归。旧任务窗口取消后断开父级通知并解除父子关系，让引用决定剩余生命周期。测试必须实际按键并运行 Qt 事件循环。
- **验证：** [任务集成测试](../tests/test_assistant_task_integration_qt.py) 覆盖真实 Esc、进行中的规划 worker、旧成功/错误回调、重复替换与单击/多击审批。文件任务草案批次曾在 `close()` 后直接 `deleteLater()` 触发 PySide6 6.8.3 测试段错误；移除该延迟删除并调整对象归属后，整组事件循环测试通过。这是具体复现的经验，不推论所有 Qt 环境都禁止 `deleteLater()`。

## 10. 多步骤任务按实际副作用结算

- **问题：** 第一步成功后取消第二步，若统一写“未修改文件”会误导；审计收尾故障若被当作写入失败，会诱发重复重试。
- **原因：** 草案、审批、文件写入和审计是四种不同状态，不能用一个成功/失败布尔值覆盖。
- **实践：** 仅准备当前步骤；每步展示固定内容，再申请一次审批。执行后先明确记入完成列表，用户另点“查看下一步”再批准。失败或取消停止剩余步骤，保留并列出已经创建的文件；成功后的审计故障作为警告。
- **验证：** [任务状态机测试](../tests/test_assistant_task_plan.py) 与 [审阅窗口测试](../tests/test_assistant_task_qt.py) 用真实临时文件系统验证部分完成、碰撞不覆盖、过期、审计警告和双击不连写；[运行时测试](../tests/test_assistant_action_runtime.py) 用同步事件验证目录切换不会改变已经展示的执行目标。

## 11. 取消要同时约束结果提交与阻塞等待

- **问题：** 只隐藏迟到文字，线程仍可能卡在等待响应头或正文；只断开连接，已经排入 Qt 队列的成功信号仍可能保存历史、触发朗读或打开草案。
- **原因：** 用户取消、HTTP 连接终止、工作线程退出和服务端推理停止是不同事件。服务端已接收的动作也不会因客户端断开而自动回滚。
- **实践：** UI 先标记本次请求取消，拒绝后续成功、错误和进度；同一 token 贯穿聊天前 PPL 状态获取及模型请求。传输层对绑定的 socket 执行 `shutdown`，让工作线程自行退出和关闭响应，不在 UI 跨线程关闭缓冲读取器或强杀线程。只有收到线程结束后才恢复发送按钮。取消的片段保留可见但不作为完整历史，输入和附件保留供重试。
- **验证：** [request_control.py](../DyberPet/assistant/request_control.py) 与 [真实 HTTP 合约测试](../tests/test_assistant_request_control.py) 覆盖请求前取消、响应头/SSE/JSON 正文等待、连接注册竞态及取消后重试；[活动 Qt 测试](../tests/test_assistant_activity_qt.py) 覆盖成功已排队、迟到错误、部分文本保留和草案不发布。它们不证明 LM Studio 已立即停止后端 GPU 推理，也不回滚已送达的 PPL 会话创建。每次 TCP 连接尝试使用最多 3 秒超时；操作系统的 `localhost` 名称解析不由本机 token 强行抢占，多地址尝试也可能增加总时长，不能据此承诺整个取消流程在 3 秒内结束。

## 12. 设备就绪不能用“任务已启动”代替

- **问题：** 模型还在加载时显示“正在监听”，或用户已停止朗读后继续排入语音并发送开始反馈，会让用户误判麦克风和声音的实际状态。
- **原因：** 启动工作线程只代表开始准备；第三方模型加载、设备打开、引擎初始化和排队播放各自可能阻塞或失败。
- **实践：** 分别呈现准备、实际活动与正在停止。麦克风 ready 仅在输入流成功打开且仍未停止时发出；模型/识别器初始化后再次检查 stop。TTS 在初始化、排队和启动循环之间检查 stop；取消后跳过后续阶段，并仍由原线程清理驱动。文案不能把播报循环时限说成可以强制打断所有驱动调用。
- **验证：** [voice.py](../DyberPet/assistant/voice.py) 与 [语音生命周期测试](../tests/test_assistant_voice_lifecycle.py) 用受控驱动验证实际阶段顺序、初始化中停止、设备打开失败不 ready，以及清理归属。驱动内部的 `init/open/read` 无法被本次事件强行抢占；这些回归证明返回后的控制流程，不证明实机可听效果或停止延迟。

## 13. 排队信号要绑定本次资源身份

- **问题：** 同一角色连续朗读两次时，上一轮迟到的 ready 可能把下一轮误标为已开始；停止监听后迟到的 partial 也可能覆盖停止提示。
- **原因：** 角色名与会话代次可以隔离切换，但不足以区分同一会话里的两次设备操作。信号发出时有效，不代表 Qt 接收时仍有效。
- **实践：** ready 携带本次 stop event 身份，接收时核对当前对象、角色/代次、停止标志和窗口状态。停止过程中不再接受部分转写更新；最终识别结果仍按当前会话交给用户确认。结果过滤与设备停止同时存在，不能彼此替代。
- **验证：** [ui.py](../DyberPet/assistant/ui.py) 的 `_on_microphone_ready`、`_on_voice_engine_ready` 和 `_heard_partial`；[活动 Qt 测试](../tests/test_assistant_activity_qt.py) 实际运行事件循环，覆盖同角色旧 ready、停止后 ready、停止后 partial 和角色切换。

## 14. 观察时间要说明起止点与统计含义

- **问题：** 一个“耗时”数字容易被误认为模型速度；用系统时间做差又会受校时影响，活动结束后继续计时则会误报等待时长。
- **原因：** 请求包含 UI 排队、可选 PPL 获取、网络等待、模型生成和回调显示；首段文字与 token、完整回复、设备就绪各不相同。
- **实践：** 用单调时钟从用户启动本次活动计时，首段记录第一段实际显示文字的时刻，字符数仅统计已展示文本。在线程结束时冻结数值，下一次活动重新计时；指标保留在本次界面状态，不额外持久化提示词、回答、音频或遥测。已完成聊天的既有 SQLite 保存策略仍独立适用。
- **验证：** [ui.py](../DyberPet/assistant/ui.py) 的活动状态方法与 [活动 Qt 测试](../tests/test_assistant_activity_qt.py) 使用受控时钟验证首段、显示字符和结束后冻结。这些值不等于 tokens/s、CPU/GPU 占用或跨设备性能结论；模型与硬件验收需要独立采样。

## 15. 用户开关要覆盖每条实际入口

- **问题：** 普通回复遵守“显示桌宠气泡”开关，TTS 开始路径却仍弹出相同气泡。
- **原因：** 同一种用户可见效果从多个信号入口触发，其中一条桥接只检查了全局设置，没有检查助手自身偏好。
- **实践：** 在真正产生效果的入口核对相关开关。朗读状态、原生动作和回复气泡分别控制；关闭气泡不应连带屏蔽语音生命周期，也不应误关已有、已解锁的说话动作。
- **验证：** [DyberPet.py](../DyberPet/DyberPet.py) 的 `_assistant_speech_started` 和 [原生桥接测试](../tests/test_assistant_speech_gait.py) 执行实际方法，检查气泡注册结果、说话状态与动作选择。既有全局气泡设置继续生效，没有安装说话素材时仍不伪造动作。

## 16. 准备失败与工作线程失败要分别收尾

- **问题：** 启动生成前读取本地历史失败，界面可能已经清空输入并进入忙碌状态，却没有真正运行的 worker 可以停止；另一种情况是手动文件动作报错，公共错误处理把仍在监听的麦克风停止事件清空了。
- **原因：** 把“展示错误”和“释放当前异步任务”放在同一个方法里，混淆了错误来源与资源归属；又在会失败的准备步骤完成前提交了 UI 状态变化。
- **实践：** 先读取并校验本地历史和记忆，成功后再清空输入、启动计时和工作线程；准备失败保留用户文字并给出可恢复提示。手动动作错误只报告该动作，只有当前 worker 的失败/结束路径才能收尾其麦克风、朗读与停止控件。
- **验证：** 检查 [ui.py](../DyberPet/assistant/ui.py) 的 `send_message`、`_job_error`、`_job_failed` 和 `_job_finished`；[活动 Qt 回归](../tests/test_assistant_activity_qt.py) 使用临时数据库及真实 worker，分别验证历史准备失败不会留下无 worker 的忙碌状态，以及无关文件错误后停止监听仍然有效。单纯检查报错文字不足以证明资源已经正确释放。

## 17. 后台回调不要延长整棵窗口的生命周期

- **问题：** 音频工作完成、窗口关闭后，保留的 ready 回调仍强引用窗口；完整套件在后续 Qt 事件循环中发生 native 段错误，单独 Qt 用例组却能通过。
- **原因：** 最小复现缩小到三项音频/取消测试及主线程 `gc.collect()`。native 栈和销毁记录显示，无父测试窗口进入循环回收时，底部 `QLabel` 的析构经过父布局通知崩溃。仅将 ready 的强窗口引用改为弱引用，同一复现即通过；没有证据把它归为某个已确认的 Qt 缺陷。
- **实践：** 设备回调保留角色、会话及本次停止事件，窗口仅使用弱引用，接收端继续核对身份和停止状态。生产助手仍由桌宠父对象持有，关闭仍等待 worker 退出。不要用禁用 GC、调整测试顺序或删除定时反馈来掩盖引用生命周期问题。另需区分 [Qt 关闭窗口](https://doc.qt.io/qt-6/qwidget.html#close) 与 [延迟删除对象](https://doc.qt.io/qt-6/qobject.html#deleteLater)：测试临时对象的清理和可复用产品窗口的关闭不能混为一谈。
- **验证：** [活动 Qt 测试](../tests/test_assistant_activity_qt.py) 的 `test_retained_audio_callback_does_not_keep_a_closed_window_alive` 分别保留朗读回调和麦克风任务，验证关闭窗口可被释放、迟到回调不再访问它。旧实现两个分支均失败，弱引用修复后通过；原三项强制 GC 复现也通过。完整套件结果按本批验证记录另列，不拿单项结果代替全量结论。

## 18. 模块替身要保留真实模块结构

- **问题：** 语音测试在 PySide6 6.8.3 通过，却在完整 PySide6 6.5.2 套件中因 `SimpleNamespace` 缺少 `__name__` 报错；仅运行纯 Python 语音用例无法发现。
- **原因：** 将模块放入 `sys.modules` 时，只提供业务方法不足以模拟模块。旧版 Shiboken 的导入钩子还会读取模块元数据；Qt 和语音测试处于同一进程时才触发这条路径。
- **实践：** 使用标准库 `types.ModuleType` 构造 sounddevice、vosk 和 pyttsx3 替身，再挂载受控驱动方法。保留真实生产捕获/播报循环及原行为断言，不降低测试范围。测试运行时应包含实际支持的 Python/Qt 组合，不能只凭更新版本通过推断旧版兼容。
- **验证：** [既有语音合约](../tests/test_assistant_persona_voice.py) 和 [语音生命周期测试](../tests/test_assistant_voice_lifecycle.py) 的模块替身均采用此结构。首轮失败证据来自 [角色导入 CI 44242637307](https://github.com/clonetimer/DyberPet/actions/runs/44242637307)；修复后的精确版本本地及远端结果见 [本批验证记录](verification/2026-11-18-assistant-activity.md) 与 PR。
